# Generative UI demo

Status: v1 built in `apps/generative-ui` and checked against Claude (`claude-haiku-5-5`) in a browser, 2026-10-26. An upstream Vite 8 / Rolldown bug leaks a dev server per in-place restart; `vp run dev` works around it (see [Dev server memory leak](#dev-server-memory-leak)). Not deployed. Work happens on `feat/generative-ui` and lands as one PR once local v1 passes `vp check`, `vp test`, and a browser check. Statements marked **unverified** have not been tested.

## Goal

A TanStack Start site where an agent answers with UI, not just text. It uses [CopilotKit](https://docs.copilotkit.ai/) in the browser and TanStack AI's `chat()` on the server, through CopilotKit's `BuiltInAgent` in TanStack mode. It mirrors the Pydantic demo: that one pairs a TanStack client with a Pydantic server, and this one pairs a CopilotKit client with a TanStack AI server, so the repository shows AG-UI working in both directions.

The agent has two ways to draw:

1. **Registered components.** Typed React components the site provides, styled with the site's Tailwind and shadcn setup.
2. **[Open Generative UI](https://docs.copilotkit.ai/generative-ui/open-generative-ui).** For anything the components don't cover, the agent writes HTML, CSS and JS that render in a sandboxed iframe.

## What was checked (2026-10-26, `@copilotkit/runtime` and `react-core` 1.80.0)

- `new BuiltInAgent({ type: "tanstack", factory: ({ input, abortController }) => chat({...}) })` runs TanStack AI. `convertInputToTanStackAI(input)` returns `messages`, `systemPrompts`, and the browser-registered `tools`. `convertTanStackStream` reads TanStack AI 1.0's AG-UI-shaped chunks. The runtime does not depend on any TanStack package.
- `createCopilotRuntimeHandler` is a fetch handler (Request in, Response out), so it fits a Start server route.
- `openGenerativeUI: { agents: [...] }` on `CopilotRuntime` gives the agent a `generateSandboxedUi` tool. The output renders in a `@jetbrains/websandbox` iframe without same-origin access. `openGenerativeUI.sandboxFunctions` on the frontend lets widget code call the host page, and `designSkill` replaces the default styling guidance.
- **Schemas:** TanStack AI 1.0 and CopilotKit 1.80 both take Standard Schema and convert it to JSON Schema through `~standard.jsonSchema`. ArkType 2.2.9 provides that (tested: draft-07 output with optional fields, enums, nested arrays). CopilotKit's own `zod ^3.25` dependency is internal and does not constrain us.
- **Streaming tool arguments:** `useRenderTool` and `useComponent` re-render with `status` going from `inProgress` (partial `parameters`) to `executing` to `complete`, plus a `toolCallId`. Neither CopilotKit nor `@tanstack/ai-react` 1.0 uses Suspense or error boundaries, so loading and error states are ours to build.
- **[TanStack Charts](https://tanstack.com/charts/latest/docs/overview) 1.1.0** (`@tanstack/charts`, React entry `@tanstack/charts/react`) renders SVG from marks such as `barY`, `barX`, `lineY`, `areaY`, `dot`, `ruleY`. A chart definition holds scale factories and functions, so it can't be JSON; the agent sends a JSON description that our code turns into `defineChart()`. Colors come from `--ts-chart-*` CSS variables. The package ships `guides/ai-authoring.md`.

## Spike findings (2026-10-26)

Verified in a browser on the dev server:

- **SSR works** once `@copilotkit/react-*` is in `ssr.noExternal`. Without it, Node tries to load the CSS file that `react-core`'s JavaScript imports and the render fails with `ERR_UNKNOWN_FILE_EXTENSION`.
- **The route works.** A splat server route (`src/routes/api/copilotkit.$.ts`, `ANY` handler) serves `createCopilotRuntimeHandler` with `basePath: "/api/copilotkit"`. `/info` reports `openGenerativeUIEnabled: true`, and a chat message reaches `chat()` and the Anthropic adapter, which fails only for want of a key. The error shows in the chat.
- **No `@ts-ignore` needed.** In 1.80, `openGenerativeUI` on `CopilotRuntime` is typed `boolean | { agents?: string[] }`.
- **`chat()` needs `threadId`.** Pass `input.threadId` and `input.runId` from the AG-UI input. The converter's `messages` and `tools` need casts to `ModelMessage[]` and `AnyClientTool[]`.
- **Schemas are typed as Standard Schema** (`StandardSchemaV1<unknown, T>`) in `defineGenComponent`, which validates through `~standard.validate`. A generic ArkType `Type<T>` doesn't line up with CopilotKit's parameter type.
- **Noise turned off:** `enableInspector={false}` on the provider hides the CopilotKit Inspector (and its browser telemetry); `COPILOTKIT_TELEMETRY_DISABLED=true` in `.env.schema` turns off runtime telemetry. `@scarf/scarf`'s install script is denied in `pnpm-workspace.yaml`.
- **Bundle size:** CopilotKit's chat pulls in Shiki and Mermaid through its markdown renderer; the client build has a 2.3 MB route chunk. Worth trimming in v1 if CopilotKit allows it.
- Two copies of `@copilotkit/core` install (one for the runtime, one for the React package, differing only in their Zod peer). They run on different sides, so this is harmless.

Checked live against `claude-haiku-5-5`:

- **Registered components work.** Claude called `callout` and it rendered with the site's styles. A follow-up run then added text after it as a separate message, so the merged-text problem seen in 1.70.1 did not appear. The text restated the callout; the system prompt should tell the agent not to.
- **Open Generative UI works.** "Build me an interactive mortgage calculator" produced a working calculator in a sandboxed iframe (`sandbox="allow-scripts"`). The first try produced it twice; see the next section.
- **The Anthropic client-tool path works** for both `callout` and `generateSandboxedUi`.

## Fixed after the spike (2026-10-26)

### The widget generated twice

Cause, from the thread's stored AG-UI events (`/api/copilotkit/threads/<id>/events`): Claude's first `generateSandboxedUi` call sent `jsExpressions` as the string `"MC.init()"` instead of `["MC.init()"]`. `chat()` validated the arguments against the tool schema, returned an error to Claude, and Claude retried correctly. But CopilotKit's middleware had already streamed the first attempt into the page, and its parser only reads `jsExpressions` as an array, so that widget never ran its init expression and stayed on screen showing $0.

Fix, in `src/server/sandbox-tool.ts`:

- `describeSandboxTool` adds field descriptions to the tool's schema, which CopilotKit sends without any. It reduced but did not remove the mistake (one in four replays still sent a string).
- `sandboxToolMiddleware`, a TanStack AI chat middleware, repairs it when it happens: `onChunk` rewrites the streamed argument deltas (adding `[` before and `]` after the string, as it streams), which is what CopilotKit renders, and `onBeforeToolCall` fixes the parsed arguments that `chat()` validates. It logs a warning when it repairs a call. Unit tests cover the stream rewriting at every split point.

Six replays of the mortgage request after the fix each made one valid call. The repair did not fire in those runs, so the live path is covered only by the unit tests and the route test.

### Dev server memory leak

Symptom: the dev server's memory grew about 400 MB per Vite restart (a `vite.config.ts` or `.env.local` change) and never came back, until Node ran out of heap after about nine restarts.

Measured by restarting eight times while recording RSS:

- No browser attached: flat. `curl` of the SSR page: nearly flat. A browser reloading after each restart: +400 MB each time. So the leak follows the client modules the browser loads.
- `apps/pydantic-agui` (Start in SPA mode, no CopilotKit): flat. A bare Vite+ app rendering CopilotKit's chat, with or without `@vitejs/plugin-react`: flat. This app without Tailwind, without `ssr.noExternal`, in SPA mode, or with import protection off: still leaking.
- V8's sampling heap profiler (over the inspector, sampling across three restarts and reading what was still alive) put most of the retained memory in Babel syntax trees allocated by Start's compiler (`start-plugin-core/dist/esm/start-compiler/compiler.js`, `compile` and `router-utils`' `parseAst`).

Cause: the Start compiler parses with Babel, and caches, every module whose code matches its detection patterns. The `ServerFn` pattern includes `\.\s*handler\s*\(` and `Middleware` is `createMiddleware`, and six of CopilotKit's pre-bundled dependency chunks (7.4 MB) match. That is about 400 MB of syntax trees per server instance for code that never uses Start. The old compilers are not freed on restart; what holds them was not found.

Fix: `vite.config.ts` wraps the `tanstack-start-core::server-fn:*` plugins so their transform skips `node_modules` except TanStack's own packages.

**Root cause found: a Vite 8 / Rolldown bug, not this app or TanStack Start.** The fix above shrank what each restart leaks; it did not stop old servers being retained. Measured after the fix with the inspector, forcing a full GC after each restart with a browser attached: the live heap grew from 220 MB to 649 MB over eight restarts, a steady 53 MB per restart. (An earlier RSS-only reading that looked flat was misleading; RSS includes garbage and moves with GC timing.) Agent runs and ordinary use without restarts don't grow it.

Heap snapshots after one and after four restarts showed one extra `Server`, `DevEnvironment`, `RunnableDevEnvironment`, `ModuleGraph`, and `WebSocketServer` per restart, all reachable only from V8's `(Global handles)`: references held by native code. Diffing what the global handles point at, per restart:

- `BindingCallableBuiltinPlugin`: Rolldown's native wrapper for a built-in plugin (`makeBuiltinPluginCallable` in `rolldown/dist/shared/normalize-string-or-regex-*.mjs`).
- `resolveSubpathImports` and `onWarn` closures (one per environment), and an anonymous closure over `getEnv`: callbacks Vite passes in the options of its native resolver, `viteResolvePlugin` (`vite:resolve-builtin`, built in `oxcResolvePlugin` in Vite's `node.js` chunk).
- `Scanner`, `TsconfigCache`, `ConnectionsList`.

The callbacks close over the old environment and config, so the whole old server, with its module graph, plugin state (including Start's compiler and its Babel trees), and watchers, stays reachable from native roots and can never be collected. Nothing on the JavaScript side releases the native wrappers when the server closes, and there is no dispose method to call.

Reproduced outside this repo with no plugins and no dependencies: a two-file app (`index.html`, `main.js`) on plain Vite 8.3.5 (Rolldown 1.2.15), restarting by touching `vite.config.mjs` and fetching the page, shows the same five objects and the same global-handle growth per restart. Vite+ 1.4.0 bundles the same Rolldown and behaves identically. The leak per restart is small for a tiny app and grows with the module graph and plugin state each server builds.

Searched `vitejs/vite`, `rolldown/rolldown`, `vitejs/rolldown-vite`, and `voidzero-dev/vite-plus` on 2026-10-26: no matching report. The nearest are Rolldown #11189 (bundled dev memory that a full GC does free) and #10985 (native allocator memory across builds). Not reported upstream; the owner decided against filing issues or pull requests with Vite or TanStack Start for now.

Workaround (2026-10-26): never restart in place. `vp run dev` runs `scripts/dev.mjs`, which starts `varlock run -- vp dev` with `GENUI_DEV_SUPERVISED=1`. The `restartInNewProcess` plugin in `vite.config.ts` then replaces `server.restart()` (used for config and `.env` changes and the `r` shortcut) with closing the server and exiting with code 75, and the script starts a fresh process. Verified: five config restarts and one `.env.local` restart each came back in a new process at a steady 900 MB, the page served after each, and Ctrl-C left no processes behind. A fresh process also lets Varlock decrypt changed values, which an in-place restart never did. Plain `vp dev` keeps Vite's own restart, and the leak.

Also worth reporting to TanStack Start: the compiler's `.handler(` heuristic matches third-party code.

## v1 findings (2026-10-26)

Checked live against `claude-haiku-5-5` in a browser, in light and dark mode:

- **npm comparison** (starter prompt): two `npmDownloads` calls, then a two-series line chart on a time axis with a legend, a `statRow` of totals and peaks, and a short summary.
- **State library** (starter prompt): four `choicePicker` questions in a row, each locking with the chosen answer highlighted once answered, then a `cardGrid` recommendation.
- **Mortgage calculator** (starter prompt): generated once, styled from `designSkill` (neutral cards, theme borders, chart tokens for the principal and interest bar), and switches to dark with the system.
- **Grouped bars with a target line**: Claude first put the target in the data as an extra row, noticed, and redrew. The chart description now says not to.

Problems found and fixed:

- **CopilotKit's chat ignored the theme.** Its stylesheet sets its own copies of the shadcn tokens on `[data-copilotkit]` and darkens only under a `.dark` class; its input also has a hard-coded white background with `cpk:dark:` variants. `style.css` makes the tokens inherit (`html:root [data-copilotkit]`, specific enough to beat `.dark [data-copilotkit]`), and an inline script in the root route keeps a `.dark` class on `<html>` in step with `prefers-color-scheme`.
- **`openGenerativeUI.sandboxFunctions must be a stable array.`** The config object is now module-level. `sendFollowUp` reaches the agent through a module-level holder that a component inside the provider fills in with `useAgent` and `copilotkit.runAgent`.
- **npm's range endpoint returned 503 for every scoped package** (`@tanstack/react-query`, `@types/node`) for a while on 2026-10-26, while unscoped packages and the point endpoint worked. `npmDownloads` falls back to one point request per month, week, or day, and reports the coarser `granularity`. The tool description tells the agent to sum finer rows when packages come back at different granularities. The range endpoint had recovered by the next run.
- **Vitest hit the same CSS import as SSR.** `test.server.deps.inline` mirrors `ssr.noExternal`. `test.env` turns off CopilotKit's runtime telemetry for test runs, which don't go through Varlock.
- **Axis ticks** showed raw numbers like `100000000`; linear axes now use compact notation.
- **Server data tools rendered nothing** and CopilotKit warned about it; they now show a one-line status (`useRenderTool`).

Tests (`vp test`, 31): every registered component's schema converts to JSON Schema; chart descriptions render to SVG through the React adapter for each mark, stacked and grouped series, empty data, and time axes with bad values; series order and colors; raw colors and too many marks are rejected; the stream repair at every split point; both data tools with a mocked `fetch`, including the point fallback; and the `/api/copilotkit` route with TanStack AI's `fakeText` adapter (a text answer, a server tool round trip, and a string `jsExpressions` repaired before the client and validation see it).

Still open besides the leak: the client bundle has a 2.5 MB route chunk (710 kB gzipped), mostly CopilotKit's markdown renderer. `Suspense` and `useSuspenseQuery` are wired up but no component fetches its own data yet, so that path is untested.
